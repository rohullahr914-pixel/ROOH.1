# Personal WhatsApp in ROOH

This is an experimental unofficial WhatsApp Web integration using whatsapp-web.js. WhatsApp can restrict accounts, disconnect sessions, or change its Web application in ways that break this integration. Use your own account and only message people who expect your messages. No bulk messaging, contact scraping, or incoming-message processing is implemented.

## Setup

1. Install Node 22 LTS and the existing Python requirements (`python -m pip install -r apps/api/requirements.txt`). Run `npm install` at the repository root. Puppeteer downloads its browser during installation. On Windows the bridge also detects installed Google Chrome. If the bundled download fails, use `$env:PUPPETEER_SKIP_DOWNLOAD="true"; npm install --legacy-peer-deps --no-audit --no-fund` in PowerShell with Chrome installed, or set `WHATSAPP_CHROME_PATH` to an installed Chrome/Chromium executable.
2. Keep existing `.env` values. Add the WhatsApp variables from `.env.example`. Generate two independent secrets using `node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"`. Set `WHATSAPP_OWNER_TOKEN` and `WHATSAPP_BRIDGE_SECRET` to different generated values, each at least 32 characters. Never use a NEXT_PUBLIC variable for secrets.
   The bridge gives the initial page 45 seconds to reach DOM readiness, then allows up to `WHATSAPP_AUTH_TIMEOUT_MS` for WhatsApp to initialize. The default is `180000` (three minutes); values below 30 seconds are ignored. Both `web.whatsapp.com` and `static.whatsapp.net` need to be reachable on the browser's network route.
3. Run the usual `npm run dev`. It starts Next, FastAPI, and the bridge. The bridge starts loading WhatsApp Web in the background so the QR can already be ready when the panel opens. Set `WHATSAPP_PREWARM=0` to start loading only on demand. A missing bridge secret or occupied bridge port fails clearly and stops the development processes. FastAPI must run as one worker: active owner voice sessions are held in memory.
4. Open ROOH at `http://localhost:3000` and click WhatsApp. Local access is established automatically with an HttpOnly session cookie; no token entry is needed. Access requires both a loopback client and an explicitly allowed loopback browser origin. If using 127.0.0.1 or another port, add that exact web origin to ALLOWED_ORIGINS and use the same hostname for the API. This is a local owner interface; do not expose the development servers publicly.
5. Opening WhatsApp or saying “ROOH, connect my WhatsApp” shows the current QR or starts the connection if needed. The connection panel shows the real QR without contact forms or connection buttons. Scan the QR using your phone's WhatsApp → Linked Devices → Link a device. QR events are authenticated and never cached or stored in browser storage. The display limit is 60 seconds from QR generation; WhatsApp can rotate the code sooner.
6. Once CONNECTED, add approved contacts by name and international E.164 phone number. The bridge verifies registration with WhatsApp. Duplicate names require selecting the exact phone number; contacts are never imported.
7. Ask ROOH to prepare a message. ROOH receives the exact draft text to read aloud. Review the recipient and message in the panel, then select Enable voice confirmation and say “Yes, send it” (also supported: “بله ارسال کن”, “بفرست”). Alternatively select Confirm & send. Confirmation expires 60 seconds after draft creation. The explicit panel action is required before speech can authorize sending; the microphone alone cannot distinguish the owner's voice from background speech.
8. Cancel through voice or the panel. Disconnect & unlink logs out the linked device. Closing the panel does not unlink it. Reconnect explicitly after connection loss; pending drafts are cancelled on voice session changes and bridge disconnection. Nothing sends automatically after reconnecting.

## Security and persistence

The bridge listens only on 127.0.0.1:3010 and requires a server secret. The owner API authenticates the browser through a signed HttpOnly, SameSite=Strict local session cookie that expires after eight hours. Creating the cookie requires a loopback peer, a loopback Host, an allowed loopback Origin, and a custom request header. Browser requests are checked against that origin and loopback restriction. The owner secret remains server-side; existing authenticated programmatic callers can still use a bearer token. The API limits requests. The four OpenAI tools can connect, check status, prepare, or cancel; none can arm or confirm a send. One-time confirmation tokens are held only by the UI, stored as hashes by FastAPI, and omitted from model responses. Drafts bind the owner, active session, contact, exact content and identifier. Incoming WhatsApp content is never forwarded to OpenAI.

LocalAuth browser credentials and the durable send-attempt journal live under `.rooh-private` at the repository root; API contacts/drafts live there when launched by the normal startup script. All private data is ignored by Git. SQLite contains plaintext message drafts and contacts; LocalAuth contains account credentials. Protect this directory and `.env` with an owner-only Windows filesystem ACL and disk encryption. Do not sync or back up these files to public storage. The integration is intended for one trusted OS account. Unix files/directories request restrictive modes; Windows access follows the parent directory's ACL.

A send identifier is durably journaled before calling WhatsApp. Repeated identifiers cannot resend, including after bridge restart. A timeout/crash produces UNCERTAIN and is never retried. Check your phone before creating another draft for the same message. SENT means WhatsApp accepted the send call; it does not prove recipient delivery or reading. The owner can query `/api/whatsapp/drafts/{id}` for controller results. No delivery/read receipt claim is made.

## Verification and manual acceptance

Automated backend tests cover authentication, denied origins, no-store responses, phone validation, unapproved contacts, exact content, confirmation arming, invalid approval, one-time tokens, cancellation, expiry, voice-session changes and uncertain sends. These tests replace WhatsApp networking and do not establish real delivery. Existing frontend tests and TypeScript checks must also pass.

Real-device acceptance remains required: verify a scannable QR, successive refresh events, authentication progress and connected account; restart ROOH to verify LocalAuth restoration; add a real consenting contact; check spoken readback, deliberate voice arming, exact send content and actual phone receipt; cancel/expire drafts; interrupt OpenAI, disable networking and close Chromium to confirm cancellation and explicit reconnection; verify no replay after a timeout or restart; unlink and confirm removal on the phone. Incoming messages must not trigger tools. Check existing media, models, voice and gesture features after these steps.

Official upstream API references: https://docs.wwebjs.dev/Client.html and https://docs.wwebjs.dev/LocalAuth.html

## Results from this implementation session

Backend controller tests and the existing frontend test suite passed; the additional frontend tests verify that OpenAI never receives confirmation tokens and that speech cannot confirm an unarmed draft. TypeScript checks passed. The real bridge started, returned no-store responses and rejected an unauthenticated status request with HTTP 401. The first browser attempt found an incomplete Puppeteer Chrome download. A second attempt using installed Chrome did not produce a QR within 90 seconds; at that stage QR generation/refresh, linking, persisted account restoration, spoken device acceptance and message receipt remained unverified. No account was linked and no message was sent. Use `python scripts/test-whatsapp-bridge.py` for a separate real-bridge check on port 3019, with an isolated temporary profile; it never links or sends. This smoke test requires WhatsApp Web network access.

Earlier full automated run: **21 backend tests passed, 42 frontend tests passed, TypeScript passed**. Installed Chrome launched successfully, but navigation to WhatsApp Web timed out after 20 seconds. Dependency installation completed successfully using installed Chrome instead of the incomplete bundled browser download.

Follow-up simplification: token entry and connection buttons have been removed from the QR flow. Opening the panel establishes a local cookie session and starts connecting. Successful real QR generation and its transmission through the authenticated FastAPI event stream have now been verified. Phone linking and message delivery still require the owner's device. The follow-up checks passed 15 WhatsApp backend tests and 5 frontend tests, including automatic local access, cookie expiry, denied remote origins/clients and duplicate bootstrap prevention. The Windows development launcher now isolates service process groups so an API reload cannot signal the frontend and bridge to stop.
